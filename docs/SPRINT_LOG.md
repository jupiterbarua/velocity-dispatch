# Sprint Log

This project is being built agile, not delivered as one batch — this file is the running record of what each week's scope was, why, and what "done" actually meant. It's also honest about the fact that a few pieces exist in the repo *ahead* of the week they logically belong to (built in an earlier pass before this week-by-week discipline started) — those are marked explicitly rather than quietly counted as finished, because a backlog that only ever shows completed work isn't a real backlog.

## What "independently working service" means here

Said out loud once so every week can be checked against the same bar, not a vibe:

1. **Owns its own persistence readiness.** Neither service assumes the other has already prepared the database — each runs its own migrations (see `services/dispatch-worker/src/db.rs::connect` for why running `sqlx::migrate!` from two services concurrently is *safe*, not racy).
2. **Owns its own startup order.** No service's `docker-compose.yml` entry (or, later, ECS service) depends on another *application* service being healthy first — only on shared infrastructure (Postgres, LocalStack/AWS).
3. **Owns its own deployable artifact.** Its own `Dockerfile`, its own ECR repository, its own ECS service (or, for the notify path, its own Lambda function) — never bundled into another service's image or task definition.
4. **Talks to its neighbors only through durable infrastructure.** SQS and EventBridge, never a direct HTTP/RPC call from one service to another. This is the one that's easy to get right by construction (it's just how the architecture is drawn) and easy to get wrong by accident (points 1 and 2 above are exactly where that accidentally leaked in before this week).

## Week 1 — walking skeleton: common + producer + consumer, local only

**Scope:** `dispatch-core` (common), `dispatch-api` (producer), `dispatch-worker` (consumer) running via `docker compose up`, talking through a real SQS queue (LocalStack), sharing nothing but the `dispatch-core` library and the Postgres schema. Explicitly **not** in scope this week: `dispatch-notify-lambda`, EventBridge, any real AWS deployment (Terraform), monitoring/dashboards. Those exist in the repo already (see "Built ahead" below) but aren't what Week 1 is being judged against.

**Acceptance criteria:**

- [ ] `docker compose up --build` brings up `postgres`, `localstack`, `dispatch-api`, `dispatch-worker` with no service waiting on another *application* service's health — only on `postgres`/`localstack`.
- [ ] `dispatch-api` and `dispatch-worker` can each be stopped and restarted independently without the other needing to restart, and without a fresh migration failing or duplicating anything.
- [ ] `POST /orders` returns `201` and the order lands in Postgres as `pending`.
- [ ] Within a few seconds (bounded by the SQS long-poll interval), `dispatch-worker` picks up the `OrderCreated` message, matches a driver (if one is registered and in range), and the order's status becomes `assigned`.
- [ ] `GET /orders/{id}` reflects that status change.
- [ ] `scripts/week1_smoke_test.sh` passes end to end (see that script for the exact checks — it's the runnable version of this checklist).

**This week's one real design decision:** `dispatch-worker` previously waited on `dispatch-api`'s health check before starting, because migrations were only run by `dispatch-api`. That's a startup-order coupling that directly violates criterion 2 above, so it's fixed this week: both services now run `sqlx::migrate!` themselves, safe because of Postgres's advisory lock during migration application (whichever process gets there first applies pending migrations; the other blocks briefly, then sees nothing left to do). `docker-compose.yml`'s `dispatch-worker` entry no longer depends on `dispatch-api` at all.

**Second decision, found during actual verification:** the first real `docker compose up --build` run (on a real laptop, not CI's runners) took over 20 minutes just compiling a single small dependency crate, because Cargo.toml's `[profile.release]` sets `lto = true` and `codegen-units = 1` — a deliberate trade-off for a faster/smaller *production* binary (see README's "Low-latency decisions"), but one that makes a from-scratch `--release` compile dramatically slower, and the AWS SDK crates in this workspace make that worse. Fixed by adding a `dev` build stage to `services/dispatch-api/Dockerfile` and `services/dispatch-worker/Dockerfile` (debug profile, no `--release`) and pointing `docker-compose.yml` at it via `build.target: dev`. CI (`ci.yml`) and `deploy.yml` both now explicitly pass `target: runtime` so the artifact that actually ships is always the fully-optimized one — the fast path exists solely for the local dev loop. `dispatch-notify-lambda/Dockerfile`'s previously-anonymous final stage was also given an explicit `AS runtime` name (was `FROM runtime` off an existing `AS runtime`-named base-image stage, which would have collided with the new convention) so all three services can be pinned to `target: runtime` uniformly rather than special-cased.

**Third decision, found immediately after the second:** even the new debug-profile `dev` build stage was still taking 20+ minutes on Jupiter's laptop — the `dev` and `builder` (release) stages are separate Docker build stages with no shared filesystem, so each one independently re-downloaded this workspace's *entire* dependency source tree from crates.io from scratch, including the large AWS SDK crates. That's a structural cost, not a hardware one. Fixed by adding BuildKit cache mounts (`RUN --mount=type=cache,target=/usr/local/cargo/registry` and `target=/app/target`) to every `cargo chef cook`/`cargo build` step in `services/dispatch-api/Dockerfile` and `services/dispatch-worker/Dockerfile`. These caches persist on the local Docker host across builds *and* across stages, so the download/compile cost is paid once total, not once per stage per build. One gotcha this introduced: a cache mount's contents don't persist into the built image layer, so each build's compiled binary is now `cp`'d out to a plain path (`/app/dispatch-api-bin` / `/app/dispatch-worker-bin`) before the `RUN` step ends, and the `runtime`/`dev` stages' `COPY --from=` lines were updated to copy from that path instead of reaching into `target/release`/`target/debug` directly.

**Fourth decision:** even with cache mounts, compiling this workspace is unrealistic on Jupiter's actual test machine (a 2015 MacBook Air — dual-core, low RAM). Rather than keep optimizing a local build that a real developer's hardware genuinely can't do quickly, `ci.yml` gained a `publish-images` job that pushes the already-tested `runtime` image (both `linux/amd64` and `linux/arm64`) to GitHub Container Registry on every push to `main`, using the repo's built-in `GITHUB_TOKEN` — no new secrets, and separate from `deploy.yml`'s push to ECR (GHCR is for "pull and run it locally"; ECR is for "this is what's running in AWS"). `docker-compose.yml` now sets both `image:` (the GHCR tag, used by `docker compose pull`) and `build:` (still available for anyone with the hardware to compile from source) on both services, so `docker compose pull dispatch-api dispatch-worker && docker compose up` needs zero local Rust compilation. This is also just a more realistic reflection of how most teams actually work — CI publishes the artifact, developers pull it, nobody's laptop is the build server.

**Status:** scope complete; local verification in progress. Four real issues were found and fixed while actually attempting to run `scripts/week1_smoke_test.sh` for the first time outside the sandbox (the `CoreError: Eq` derive bug, the missing local-dev build profile, the missing cache mounts, and finally moving image builds to CI entirely given the test machine's hardware) — that run still hasn't completed successfully yet with all fixes in place. Note: the GHCR package must be set to public visibility (or Jupiter needs to `docker login ghcr.io` with a PAT that has `read:packages`) before an anonymous `docker compose pull` will succeed — GitHub Actions creates newly-pushed packages as private by default.

**Fifth issue, also from real CI output (`fmt + clippy`):** `services/dispatch-api/src/error.rs` line 14 and `services/dispatch-api/src/sqs.rs` line 19 both exceeded rustfmt's 100-char line width with the same unwieldy type: `aws_sdk_sqs::error::SdkError<aws_sdk_sqs::operation::send_message::SendMessageError>`. Fixed with a `pub(crate) type SqsSendError = ...` alias in `error.rs`, used in both places — shorter and more readable, not just technically compliant. Checked `dispatch-worker`'s equivalent EventBridge publisher and confirmed it returns `anyhow::Result<()>` instead of a concrete SDK error type, so it never hits the same problem.

**Sixth issue, and a process correction:** Jupiter pasted a third individual fmt diff (`dispatch-worker/src/main.rs`'s `publisher` line). At that point it became clear these would keep surfacing one at a time — and it turned out unnecessary to keep doing that. `rustfmt` is a standalone syntax formatter; unlike `cargo check`/`clippy`/`test`, it never needs to fetch or compile actual dependency crates, so it runs fine even in a sandbox with no crates.io access. Running the real `cargo fmt --all` (not just `--check`) directly here fixed every remaining formatting issue across the whole workspace in one pass, confirmed by a clean `cargo fmt --all -- --check` afterward. This should have been the first move instead of hand-fixing individual pasted diffs — noted so future rounds run `cargo fmt --all` proactively after any Rust edit instead of waiting for CI to report violations one at a time.

**Seventh issue, a real clippy lint (found once the `fmt` issues cleared and the sync/push finally happened):** `crates/dispatch-core/src/geo.rs`'s `nearest_driver` declared an explicit `'a` lifetime (`pub fn nearest_driver<'a>(pickup: GeoPoint, candidates: &'a [Driver], radius_km: u32) -> Result<(&'a Driver, f64), CoreError>`) that Rust's lifetime elision rules can already infer on their own — one input reference, one output reference, so the compiler doesn't need it spelled out. `ci.yml`'s clippy step runs with `-D warnings`, turning this into a hard failure (`clippy::needless_lifetimes`). Fixed by removing the explicit lifetime entirely, exactly as clippy's own suggested fix showed. Checked the rest of the workspace for the same pattern (grepped for `<'[a-z]` across every `.rs` file) — this was the only explicit lifetime anywhere in the codebase. Also worth noting: this lint took ~45 minutes to surface in CI on a cold cache, since `clippy` — like `cargo test`/`build` — needs to fully type-check the whole dependency graph (same cost as a debug compile), and this workspace's AWS SDK crates are large. `ci.yml`'s `lint` job already uses `Swatinem/rust-cache@v2`, so this should have been a one-time cold-cache cost, not a recurring one.

**Eighth issue, another real clippy lint, this time on `services/dispatch-api/src/sqs.rs`:** `OrderEventPublisher::publish` returned `Result<(), SqsSendError>` where `SqsSendError` is a bare `aws_smithy_runtime_api::client::result::SdkError<...>` — clippy's `result_large_err` flagged it because that error variant is at least 368 bytes (an `SdkError` embeds a full HTTP response), meaning every `Result<(), SqsSendError>` on the stack pays for the largest variant even on the `Ok` path. Fixed by boxing it at the alias site in `error.rs` — `pub(crate) type SqsSendError = Box<aws_sdk_sqs::error::SdkError<...>>` — rather than boxing at every call site. `Box<T>` implements `From<T>` in the standard library, so the `?` operator in `sqs.rs::publish` needed no change at all; the alias absorbed the whole fix. Also confirmed via the same workspace-wide `grep` habit as the Seventh issue that `dispatch-worker`'s EventBridge publisher (which returns `anyhow::Result<()>`, not a concrete SDK error) doesn't share this problem, so nothing else needed the same treatment. Sanity-checked the fix with `rustfmt --check` directly (no network needed) before pushing, rather than waiting on another 45-minute cold-cache CI round-trip to confirm formatting.

**Ninth issue, a real Docker build failure in the `docker-build` CI job (`dispatch-notify-lambda` only):** `cargo chef prepare --recipe-path recipe.json --bin bootstrap -p dispatch-notify-lambda` failed with exit code 2 (a CLI usage error) at the `planner` stage. Comparing against `dispatch-api`/`dispatch-worker`'s Dockerfiles — whose `prepare` steps only ever pass `--recipe-path` and `--bin`, never `-p` — showed the actual bug: `cargo chef prepare` doesn't accept a `-p`/`--package` flag at all (that belongs on `cargo chef cook`, further down in the same Dockerfile, which correctly has it). The extra `-p dispatch-notify-lambda` on the `prepare` line was the mistake. Fixed by removing it, leaving `cargo chef prepare --recipe-path recipe.json --bin bootstrap` — now consistent with the other two Dockerfiles' pattern.

**Tenth issue, five files failing `terraform fmt -check -recursive`:** `dashboard.tf`, `ecs.tf`, `monitoring.tf`, `rds.tf`, `sqs.tf` were all flagged. `terraform` itself isn't installed in this sandbox and can't be fetched here (same blocked-network issue as `cargo check`), so each file was checked by hand against terraform's documented alignment rule (consecutive single-line attributes in the same block get their `=` signs padded to line up on the longest key, reset by a blank line or a nested multi-line block). Found and fixed five genuine, narrow misalignments, each traceable to a real prior edit that was never re-run through `terraform fmt`:
- `rds.tf`: `instance_class`/`allocated_storage`/`storage_type` were padded to an old, wider column left over from a previous version of that block.
- `sqs.tf`: `maxReceiveCount` had one extra space relative to `deadLetterTargetArn`.
- `ecs.tf`: `container_name`/`container_port` in the `load_balancer` block each had one extra space relative to `target_group_arn`.
- `monitoring.tf`: both the `api_running_below_desired` and `api_5xx_rate` alarms have a `dimensions = { ... }` block that spans multiple lines (two dimension keys each) — that splits the surrounding attributes into two separate alignment groups instead of one, so `alarm_name`/`alarm_description`/`namespace`/`metric_name` needed to shrink to their own group's (narrower) column instead of the wider one shared with `statistic`/`comparison_operator`/etc. Likely left over from when `dimensions` was a single-line value (like the other three alarms in this same file, which only ever needed one dimension key and were never touched).
- `dashboard.tf`: the "Match outcomes by type" widget's `title`/`region`/`view` were one column too narrow — a `stacked = true` line was added to that widget (to render it as a stacked chart) without re-running `terraform fmt`, which widened the group's longest key and should have re-padded the other three lines too.

Not fully verifiable without a real `terraform fmt` run — flagged so Jupiter can confirm with `terraform fmt -check -recursive` in `infra/terraform` locally (this is a lightweight static binary, unlike the Rust workspace, so it should run fine even on the 2015 MacBook Air) and paste back anything still flagged.
